All backend secrets live in **one file on the server**, `~/vod-app/infra/prod.env`, which is git-ignored and never leaves the server. Frontend values live in the Vercel project settings. Nothing secret is committed to the repository.

## Inventory

| Secret | Protects | Read by |
|---|---|---|
| `POSTGRES_PASSWORD` (inside `DATABASE_URL_SYNC` / `DATABASE_URL`) | The database | postgres, api, worker |
| `REDIS_PASSWORD` | Redis: Celery queue, processing lock, upload slots | redis, api, worker |
| `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | MinIO administrator | minio |
| `minio_access_key` / `minio_secret_key` | S3 access used by the backend and tusd | api, worker, tusd |
| `jwt_secret_key` | Signing of every access and refresh token | api, worker |
| `tus_hook_shared_secret` | tusd → API hook calls | api, tusd |
| `RESEND_API_KEY` | Sending email as the platform | api, worker |
| `PGADMIN_DEFAULT_PASSWORD` | pgAdmin (local development only) | — in production |
| Vercel: `NEXT_PUBLIC_API_URL` | Not secret (public in the bundle) | frontend build |

`NEXT_PUBLIC_*` values are compiled into JavaScript that every visitor downloads, so they must never contain anything secret.

## Rules

- Generate values with a password manager or `openssl rand -base64 48`.
- Never reuse the defaults from `.env.example` or `docker-compose.local.yml`.
- Never paste `prod.env` into chats, issues or screenshots. Share variable **names** when asking for help.
- Keep an offline copy of `prod.env` in a password manager; it is not backed up anywhere else.

## Rotation

Edit the value in `prod.env`, then restart the containers that read it. Some secrets also need a change inside the service itself.

<Tabs items={['JWT key', 'Redis', 'PostgreSQL', 'MinIO', 'tus hook', 'Resend']}>
<Tab value="JWT key">

```bash
dc up -d --force-recreate api worker
```

Every existing access and refresh token becomes invalid immediately, so **all users are signed out**. Use this as the emergency response to a suspected key leak.

</Tab>
<Tab value="Redis">

```bash
dc up -d --force-recreate redis api worker
```

Redis takes its password from its start command, so recreating it applies the new value. Do this while nothing is processing: recreating the worker runs startup recovery, which fails any in-progress video and clears pending task messages (re-queue it afterwards).

</Tab>
<Tab value="PostgreSQL">

The password is stored inside the database's data volume when it is first created, so changing the env file alone does nothing. Change it in PostgreSQL first, then in `prod.env` (`POSTGRES_PASSWORD` and both database URLs):

```bash
dc exec postgres psql -U vod_user -d vod_db -c "ALTER USER vod_user WITH PASSWORD '<new>';"
dc up -d --force-recreate api worker
```

</Tab>
<Tab value="MinIO">

First check whether `minio_access_key` / `minio_secret_key` are the same as `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` in `prod.env`.

- **If they are the root credentials:** change both pairs to the new values together, then `dc up -d --force-recreate minio api worker tusd`. Object data is kept in the `minio_data` volume.
- **If they are a separate MinIO user:** create a new access key for that user, update the pair, recreate `api`, `worker` and `tusd`, then delete the old key.

</Tab>
<Tab value="tus hook">

```bash
dc up -d --force-recreate api tusd
```

Both sides must change together. Uploads that start during the restart are rejected and can be retried.

</Tab>
<Tab value="Resend">

Create a new key in the Resend dashboard, update `RESEND_API_KEY`, recreate `api` and `worker`, then revoke the old key.

</Tab>
</Tabs>

## After a suspected leak

1. Rotate the leaked secret (JWT key first if unsure: it signs everyone out).
2. Check `dc logs api` for unusual admin activity around the time of the leak.
3. Review recently created users and admins:

```sql
SELECT email, role, created_at FROM users ORDER BY created_at DESC LIMIT 20;
```
