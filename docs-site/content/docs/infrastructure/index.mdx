## The backend server

Seven containers on one host, defined in `infra/docker-compose.yml`:

| Service | Image | Network exposure |
|---|---|---|
| `caddy` | `caddy:2-alpine` | **Host network**: the only public entry point (ports 80 and 443) |
| `api` | built from `backend/` | Loopback only (`127.0.0.1:8000`) |
| `worker` | built from `backend/` (same image) | None |
| `postgres` | `postgres:16-alpine` | None (private Docker network) |
| `redis` | `redis:7-alpine` | None (private Docker network) |
| `minio` | `minio/minio` | Loopback only (`127.0.0.1:9000`); the admin console is not published |
| `tusd` | `tusproject/tusd:v2.9.2` | Loopback only (`127.0.0.1:1080`) |

All services except Caddy share a private bridge network (`backend_net`) and reach each other by service name (`postgres:5432`, `redis:6379`, `minio:9000`, `api:8000`). Caddy runs on the host network and reaches the three services it proxies through their loopback ports.

## Why one server

The project is built to show that a complete VOD platform can run on a small, inexpensive server. That choice drives several decisions documented elsewhere:

- The worker processes one video at a time ([ADR 0002](/docs/decisions/adr-0002-processing-queue)).
- Each container has a **memory limit**, so a heavy transcode cannot starve the database or the API.
- Video bytes bypass Python on the way in (tusd) and on the way out (Caddy → MinIO).

## Resource budget

Memory limits from the production compose file:

| Service | `mem_limit` | Notes |
|---|---|---|
| worker | 1800 MB | FFmpeg needs the most headroom; CPU weight lowered (`cpu_shares: 256`) so the API wins under contention |
| api | 768 MB | `cpu_shares: 1024` |
| postgres | 512 MB | |
| minio | 512 MB | |
| redis | 256 MB | |
| tusd | 192 MB | |
| caddy | 64 MB | |

`cpu_shares` are relative weights, not hard caps: they only matter when processes compete for CPU.
