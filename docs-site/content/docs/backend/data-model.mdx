## users

| Column | Type | Notes |
|---|---|---|
| `id` | string (UUID) | Primary key |
| `email` | string | Unique, indexed |
| `username` | string | Unique, indexed |
| `hashed_password` | string | bcrypt |

Two columns describe two different things and are easy to confuse:

- **`status`** is editorial: has an admin published it?
- **`processing_status`** is technical: how far has the pipeline got?

A video can be `published` while still `transcoding`; the player shows "still processing" until `manifest_url` is set.

## email_verification_tokens and password_reset_tokens

Both have the same shape: `user_id` (cascade delete), `token`, `expires_at`, `used`, `created_at`. Verification tokens are UUIDs valid for 24 hours; reset tokens are 6-digit codes valid for 1 hour.

## tus_uploads

One row per resumable upload session.

| Column | Notes |
|---|---|
| `upload_id` | Primary key; the tus upload ID assigned in the `pre-create` hook |
| `user_id` | → `users.id` |
| `video_id` | → `videos.id`, set when the upload finishes |
| `object_key` | Where the file landed in MinIO |
| `declared_size` | Bytes, from the client |
| `status` | `created`, `completed` or `terminated` |
| `created_at`, `completed_at` | |

## Migrations

Alembic migrations live in `backend/alembic/versions/` as a single linear chain. They are run manually (`alembic upgrade head`). At startup the API also calls `create_all()`, which creates any table that does not exist yet but never alters existing ones.

## Design notes

- **Status columns are strings, not database enums.** Adding a pipeline stage needs no migration; the allowed values are enforced in Python (`ProcessingStatus`).
- **Soft delete** keeps rows (and their files) when an admin deletes a video; queries filter on `deleted_at IS NULL`.
- **Paths, not URLs**, are stored for every file, so the public host can change without touching data.
